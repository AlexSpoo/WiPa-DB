## 1. Kritischer Bug: mehrzeilige Textfelder erzeugten kaputte YAML-Dateien

**Symptom:** Beim Transkribieren mit dem neuen auto-wachsenden Textfeld (aus
dem vorletzten Fix) konnte eine Notiz entstehen, die sich nicht mehr einlesen
ließ — mit Folgefehlern an mehreren Stellen (siehe Punkt 3 und 4).

**Ursache:** `yamlScalar()` in `transcribe.js` prüfte nicht, ob ein Wert einen
Zeilenumbruch enthält. Ein roher `\n` in einem nicht in Anführungszeichen
gesetzten YAML-Wert ergibt ungültiges YAML.

```js
// vorher
function yamlScalar(value) {
    if (value === "" || value === null || value === undefined) return "";
    const needsQuotes = /^[[{>|*&!%#`"'@,?-]/.test(value) || value.includes(": ") || value !== value.trim();
    return needsQuotes ? JSON.stringify(value) : value;
}

// nachher
function yamlScalar(value) {
    if (value === "" || value === null || value === undefined) return "";
    const needsQuotes = /^[[{>|*&!%#`"'@,?-]/.test(value)
        || value.includes(": ")
        || value.includes("\n")
        || value.includes("\r")
        || value !== value.trim();
    return needsQuotes ? JSON.stringify(value) : value;
}
```

**Reale Auswirkung geprüft:** Nur eine einzige Datei im gesamten Vault war
betroffen (`Screenshots/TESTPROJEKT/Screenshot_TEST-P-001.md`, aus deinem
Test). Ich habe sie manuell repariert (Wert korrekt in Anführungszeichen
gesetzt) und mit `js-yaml` erneut geprüft — liest sich jetzt korrekt ein.
Alle anderen Notizen im Vault wurden durchgecheckt, keine weiteren Treffer.

## 2. `loadUnlinkedScreenshots()` fand keine Screenshots beim Personen-Transkribieren

**Symptom:** Du konntest beim Transkribieren einer Person keine Screenshots
auswählen, obwohl vorher welche transkribiert wurden.

**Ursache:** Zwei Probleme gleichzeitig:

1. Die Funktion las nur eine Ordnerebene tief (`readDir` ohne Rekursion) —
   bei Projekten mit Event-Unterordnern (MOSAIQ) wurden Screenshots nie
   gefunden.
2. Da sie nicht gegen Fehler abgesichert war, hat die kaputte YAML-Datei aus
   Punkt 1 die komplette Funktion mit einem unbehandelten Promise-Reject
   abbrechen lassen — auch für Screenshots, die eigentlich lesbar gewesen
   wären.

```js
// vorher
async function loadUnlinkedScreenshots(personenordner) {
    const dir = await join(screenshotsDir, personenordner);
    const screenshots = [];
    if (!(await exists(dir))) return screenshots;

    for (const entry of await readDir(dir)) {
        if (!entry.isFile || !entry.name.endsWith(".md")) continue;
        const data = await readFrontmatter(await join(dir, entry.name));
        if (data?.Person) continue;
        screenshots.push({ fileName: entry.name.replace(/\.md$/, ""), id: data?.ID ?? entry.name });
    }
    return screenshots.sort((a, b) => a.id.localeCompare(b.id));
}

// nachher
async function loadUnlinkedScreenshots(personenordner) {
    const dir = await join(screenshotsDir, personenordner);
    const screenshots = [];

    for (const filePath of await collectMdFilesRecursive(dir)) {
        const data = await safeReadFrontmatter(filePath);
        if (!data || data.Person) continue;
        const fileName = (await basename(filePath)).replace(/\.md$/, "");
        screenshots.push({ fileName, id: data?.ID ?? fileName });
    }
    return screenshots.sort((a, b) => a.id.localeCompare(b.id));
}
```

`collectMdFilesRecursive()` und `safeReadFrontmatter()` sind neue Helfer (siehe
Punkt 3) und werden jetzt konsistent überall verwendet, wo mehrere Notizen
durchsucht werden.

## 3. Robustheit: eine kaputte Notiz darf nie wieder alles lahmlegen

Zusätzlich zum eigentlichen Bugfix in Punkt 1 habe ich die Sammel-Funktionen
defensiv gemacht, damit ein einzelner beschädigter Eintrag (aus welchem Grund
auch immer) nur diesen einen Eintrag überspringt, statt die ganze Seite
abstürzen zu lassen:

```js
// transcribe.js und evaluate.js (gleiches Muster in beiden Dateien)
async function safeReadFrontmatter(filePath) {
    try {
        return await readFrontmatter(filePath);
    } catch (err) {
        console.warn(`Konnte Frontmatter nicht lesen, überspringe: ${filePath}`, err);
        return null;
    }
}
```

Verwendet jetzt in: `loadExistingPersons()`, `loadUnlinkedScreenshots()`
(beide `transcribe.js`) und `readAllNotesRecursive()` (`evaluate.js`).
Zusätzlich in `evaluate.js` das `change`-Event mit try/catch umschlossen, so
dass bei einem unerwarteten Fehler wenigstens eine Meldung erscheint statt
gar nichts zu passieren.

## 4. MOSAIQ-Notizen wurden nicht gefunden (Personen **und** Screenshots)

**Symptom:** "Fast alle Events nicht transkribiert" — betraf konkret alle
MOSAIQ-Events (Moosach 1/2, Schwabing 1/2), also die Hälfte aller Events.

**Ursache:** Garching/IAA legen ihre Notizen flach ab
(`Personen/Garching/Person_X.md`), MOSAIQ dagegen pro Event verschachtelt
(`Personen/MOSAIQ/Moosach/Person_X.md`,
`Screenshots/MOSAIQ/Moosach 1/Screenshot_X.md`). `loadExistingPersons()` und
die "schon transkribiert?"-Prüfung für Screenshots lasen bisher nur eine
Ordnerebene tief.

**Fix:** Ein rekursiver Datei-Sammler, der beide Strukturen abdeckt:

```js
async function collectMdFilesRecursive(dir) {
    const files = [];
    if (!(await exists(dir))) return files;

    for (const entry of await readDir(dir)) {
        const entryPath = await join(dir, entry.name);
        if (entry.isDirectory) {
            files.push(...(await collectMdFilesRecursive(entryPath)));
        } else if (entry.isFile && entry.name.endsWith(".md")) {
            files.push(entryPath);
        }
    }
    return files;
}
```

`loadExistingPersons()` und die neue `collectExistingScreenshotIds()` (für die
Screenshot-Batch-Erkennung) nutzen das jetzt beide, statt selbst einen
flachen `readDir()`-Aufruf zu machen. Ausführlich mit `find` im Vault
gegengeprüft, dass diese Verschachtelung tatsächlich nur bei MOSAIQ vorkommt.

## 6. CSV-Export: Screenshots-Spalte uneinheitlich formatiert

**Symptom:** Manche Einträge zeigten `Screenshots/Garching/Screenshot_G-MG-005`,
andere nur `Screenshot_G-P-002`.

**Ursache:** Keine App-seitige — das ist eine **bestehende Inkonsistenz in
alten Vault-Daten** (manche historischen Personen-Notizen verlinken
Screenshots mit vollem Pfad im Wikilink selbst, z. B.
`"[[Screenshots/Garching/Screenshot_G-MG-009]]"`, andere nur mit dem Namen).
Kommt vermutlich aus der Zeit vor dieser App.

**Fix (nur Anzeige/Export, Vault-Daten unangetastet):**

```js
// evaluate.js
function extractWikilinkTarget(value) {
    if (typeof value !== "string") return value;
    const match = value.match(/\[\[(.+?)(\|.*)?\]\]/);
    const target = match ? match[1] : value;
    return target.includes("/") ? target.slice(target.lastIndexOf("/") + 1) : target;
}
```

Nimmt jetzt immer nur den letzten Pfad-Teil, unabhängig davon, wie der
Wikilink ursprünglich geschrieben wurde.

## 7. Screenshot-Nummerierung kollidierte zwischen Events desselben Projekts

**Symptom:** Beim Umbenennen von Screenshots für Garching 2 wurden
versehentlich Nummern vergeben, die in Garching 1 schon existierten
(`G-P-001`–`G-P-003` doppelt) — dadurch zeigten alte Garching-1-Einträge auf
die neuen Garching-2-Bilder.

**Ursache:** `computeNextScreenshotNumber()` in `rename.js` hat die nächste
freie Nummer nur im RAW-Ordner des **aktuellen** Events gesucht. Präfix und
Kürzel sind aber projektweit fest (nicht pro Event) — Garching 1 und 2 teilen
sich denselben Namensraum, weil ihre Screenshot-**Notizen** ja auch in einem
gemeinsamen, nicht nach Event getrennten Ordner landen.

```js
// nachher — scannt jetzt alle Events desselben Projekts, nicht nur das aktuelle
async function computeNextScreenshotNumber(eventName, typeKürzel, screenshotType, rules) {
    const prefix = eventInfo[eventName]?.screenshotPrefix ?? "";
    const projektName = eventInfo[eventName]?.projektName;

    let highest = 0;
    const pattern = new RegExp(`^${prefix}${typeKürzel}-(\\d+)`);

    const relatedEventNames = Object.keys(eventInfo).filter((name) => eventInfo[name]?.projektName === projektName);
    for (const relatedEventName of relatedEventNames) {
        const eventPath = await resolveEventFolder(screenshotDir, relatedEventName);
        if (!(await exists(eventPath))) continue;
        const files = await readDir(eventPath);
        for (const file of files) {
            const match = file.name.match(pattern);
            if (!match) continue;
            const number = parseInt(match[1], 10);
            if (number > highest) highest = number;
        }
    }

    const batchHighest = highestBatchNumber((state) =>
        state.type === "screenshot" && eventInfo[state.event]?.projektName === projektName && state.screenshotType === screenshotType
    );
    if (batchHighest > highest) highest = batchHighest;

    return String(highest + 1).padStart(rules.counterDigits, "0");
}
```

**Bereits entstandene Kollision repariert:** Die drei versehentlich
duplizierten Garching-2-Dateien wurden umbenannt, um an die bestehende
Nummerierung anzuschließen (G-P-001–007 waren schon vergeben):

- `Screenshots(RAW)/Garching 2/G-P-001.jpg` → `G-P-008.jpg`
- `Screenshots(RAW)/Garching 2/G-P-002.jpg` → `G-P-009.jpg`
- `Screenshots(RAW)/Garching 2/G-P-003.jpg` → `G-P-010.jpg`

Geprüft über den `Person:`-Link in den bestehenden Screenshot-Notizen
`Screenshot_G-P-001` bis `-007`, welche Events sie tatsächlich betreffen
(001–004 → Garching 1, 005–007 → Garching 2), damit klar war, welche der
beiden gleichnamigen Dateien die "falsche", neu hinzugekommene ist.
Anschließend über den ganzen `Screenshots(RAW)`-Ordner nach weiteren
doppelten Dateinamen gesucht — keine weiteren gefunden.

**Offene Grundsatzfrage von dir:** du hattest überlegt, ob man stattdessen
einen RAW-Ordner pro Projekt (statt pro Event) anlegen sollte. Der jetzige
Fix löst das Problem, ohne Ordner umzustrukturieren — schau morgen, ob dir
das reicht oder ob du die Ordnerstruktur trotzdem vereinheitlichen willst.

```diff
     for (const field of templateFields) {
```

"Zusätzliche Anmerkungen" ist jetzt ein ganz normales Feld, das jedes
Screenshot-Template selbst führen muss (habe ich bei allen 14 Templates

Liste **aller** registrierten Vaults (nicht nur der anderen wie beim
Umschalten), mit "Entfernen"-Button pro Eintrag außer dem gerade aktiven

dasteht). "Entfernen" nimmt den Eintrag nur aus der Liste in `settings.json`
— löscht keine echten Dateien, jederzeit über "+ Neue Datenbank" wieder
hinzufügbar.

```js
// dashboard.js
```
